# src/middleware

Express middleware, wired together per-route in `src/routes/*.ts` (there is no single global auth/validation middleware — each route composes exactly what it needs, e.g. `requireAuth, requireDb, validateParams(schema), someController`).

### Auth gates
- **`requireAuth.ts`** — `requireAuth` only checks a `Bearer <token>` header is *present*, not that it's valid. `getBearerToken(req)` (exported, reused everywhere) is the real workhorse — every service function that needs the caller's identity calls `verifyAccessToken(getBearerToken(req))` itself (see `src/services/*`'s repeated `requireUserId(accessToken)` pattern). **Gotcha**: don't assume a route protected by bare `requireAuth` has already verified the token — it hasn't; the real check happens deeper, inside whichever service the controller calls.
- **`requireAdminAuth.ts`** — by contrast, this one *does* fully verify (`verifyAdminAccessToken`), sets `req.adminUserId`, and rejects with 401 itself. Admin and customer tokens carry different JWT `typ` claims (`"admin"` vs `"access"`) and are mutually rejected by each other's verifier — confirmed by `tests/integration/adminAuth.integration.test.ts`.
- **`requireDb.ts`** — a simple `hasDatabase` (from `src/env.ts`) check, 503s with a clear message if `DATABASE_URL`/`JWT_SECRET` aren't set. Mounted on nearly every DB-backed route so a misconfigured deployment fails loudly and specifically instead of every route throwing its own generic error.

### Rate limiting
All five limiter files use `rate-limiter-flexible`'s `RateLimiterRedis`, and as of the Redis-outage hardening pass, all five now agree on what happens when Redis itself is unreachable (a *rejection* that isn't a real "limit exceeded" — no `msBeforeNext` on the thrown value): they **fail open**, via one shared helper, `consumeOrFailOpen` (`rateLimitShared.ts`) — a rejection only 429s when it actually carries `msBeforeNext` (a real, points-exhausted rejection); anything else (a genuine Redis/network failure) falls through to `next()` and lets the request proceed. A Redis outage must never be indistinguishable from a user-caused rate limit.

- **Insured, never unlimited (CS-09)** — `rateLimitAuthFlows.ts` (login, OTP send/verify, password forgot/reset, signup, verify-email, resend-verification) and `rateLimitAdminLogin.ts` use `createInsuredLimiter` / `consumeInsured` (`rateLimitShared.ts`): a `RateLimiterRedis` with a bounded in-memory `insuranceLimiter` (`BoundedMemoryLimiter`, keys hashed into 65,536 buckets) and `rejectIfRedisNotReady`. A Redis outage degrades to a per-instance cap; if even the in-memory fallback errors, the request gets a 429 (fail closed). Login, admin login, OTP, password-forgot and signup are keyed per IP **and** per normalised (NFKC, trimmed, lowercased, SHA-256) email over a 15-minute window; resend-verification per IP and per user.
- **`rateLimitPublicAttachment.ts`**, **`rateLimitPublic.ts`'s `rateLimitPublicChat`** — have an in-memory `insuranceLimiter`, but still fail open via `consumeOrFailOpen` if both layers error (the widget must not go dark over infra).
- **`rateLimitAuthenticatedChat.ts`**, **`consumeStrictPublicChatLimit`** — no fallback; unchanged.
- `req.ip` feeds every key: `TRUST_PROXY_HOPS` must equal the proxy hop count (production: `1`); `0` ignores `X-Forwarded-For`. See `resolveTrustProxy` in `src/app.ts`.
- **`rateLimitPublic.ts`'s `limitPublicChatConcurrency`** is a different mechanism entirely (a per-chatbot concurrency slot, not a request-rate limit) and is deliberately **fail-closed** (503 on a Redis timeout) — a late-arriving Lua command might still complete after the client-side timeout, so proceeding could exceed the configured ceiling. Not part of the fail-open family above.

Tests: `tests/unit/rateLimitFailOpen.test.ts` (the middleware-level fail-open/fail-closed funnel, all five limiter files) and `tests/unit/rateLimitInsuranceLimiter.test.ts` (the real `insuranceLimiter` fallback engaging against a broken `storeClient`, not just a mocked `.consume()`).

If you're adding a sixth rate limiter, reuse `consumeOrFailOpen` from `rateLimitShared.ts` rather than reimplementing the check — and decide deliberately whether it needs an `insuranceLimiter` too.

### Request plumbing
- **`asyncHandler.ts`** — wraps an async Express handler so a rejected promise reaches Express's error-handling chain (`next(err)`) instead of becoming an unhandled rejection. Every controller in `src/controllers/` is wrapped in this.
- **`errorHandler.ts`** — the final error-handling middleware (mounted last in `src/app.ts`). Turns a thrown `AppError` into its own `{status, message}`, a JSON body-parse failure into a clean 400, and anything else into a logged 500 with a generic message (never leaks a raw stack trace to the client).
- **`requestId.ts`** — mounted *first* in `src/app.ts`, before `helmet`/`cors`. Reads (or generates) a request id, sets it on `req.id` and the `X-Request-Id` response header, and runs the rest of the request inside `runWithRequestId` nested with an empty WP-3.1 tenant ALS (`src/lib/tenantContext.ts`).
- **`tenantContext.ts`** — `bindTenantContext`, mounted after JSON parsing. Copies a verified access/admin JWT and public-widget chatbot id into ALS. Owner routes still wait for `requireOwnedChatbotId` before `app.chatbot_id` is set.
- **`validate.ts`** — `validateBody(schema)` / `validateParams(schema)`, thin Zod wrappers. **Asymmetry worth knowing**: `validateBody` replaces `req.body` with Zod's *parsed* output (so defaults/coercions from the schema actually apply downstream); `validateParams` validates but does **not** reassign `req.params` — a controller reading `req.params.foo` after `validateParams` still sees the raw string, not a schema-transformed value (harmless today since every param schema here is just `.uuid()` with no transform, but would matter if one ever added a `.transform()`).
- **`uploadDocument.ts`** — multer (memory storage, single `file` field, 20MB hard cap) wrapped so multer's own error shape (e.g. `LIMIT_FILE_SIZE`) is translated into this app's `AppError`/JSON error shape instead of the generic 500 the global `errorHandler` would otherwise give it. Used only by the document-ingestion upload route (`POST /chatbots/:id/documents`).
