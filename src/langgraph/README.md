# src/langgraph

Three separate LangGraph (`@langchain/langgraph`) conversational state machines, all Full Custom plan only, all built on the same "propose → confirm → commit" shape: a node extracts/proposes something, a confirmation node pauses the graph (via LangGraph's `interrupt`) until the human replies, and only after that does a dedicated commit node make the one real, state-changing external call. This directory owns the *conversation flow*; the actual external API calls live in `src/lib/bookly/`/`src/lib/woocommerce/`, and the actual commit/idempotency logic lives in `src/services/booklyBooking.service.ts`/`commerceOrder.service.ts` — the graphs call *into* those services, they don't inline the write themselves.

**Shared infrastructure:**
- **`checkpointer.ts`** — `getCommerceCheckpointer()`, a lazily-created, process-wide singleton `PostgresSaver` (real Postgres-backed LangGraph checkpointing, using the same `DATABASE_URL`). **Gotcha**: despite the "Commerce" name, this one checkpointer backs **both** the Bookly graph and the Commerce graph (`booklyGraph.ts` and `commerceGraph.ts` both import it) — it's shared infra, not commerce-specific, the name is just a naming artifact from whichever graph was built first. Checkpointing is what makes `interrupt`/`Command({resume})` durable across separate HTTP requests: each incoming chat message is its own `graph.invoke()` call, resumed by `thread_id` (the conversation id), not a long-lived in-memory process.
- **`llm.ts`** — `getCommerceLlm()`, a **separate** LLM client from `src/lib/ai.ts`'s multi-provider (Claude/Gemini/OpenAI/Ollama) fallback chain used for normal chatbot answering. This one is hardcoded to `ChatOpenAI({ model: "gpt-4o-mini" })` via LangChain, used for structured intent-classification/extraction inside every graph in this directory. **Important operational consequence**: if `OPENAI_API_KEY` isn't set, none of Bookly/Commerce/Bookly-admin conversational flows work at all — there is no fallback to Anthropic/Gemini for this part of the system, independent of whatever other provider keys are configured for the main chat pipeline.

### Customer-facing booking flow (Bookly)
- **`booklyState.ts`** — the graph's typed state (`BooklyState`, a LangGraph `Annotation.Root`): `intent`, `selectedResourceId`, `availableSlots`, `bookingDraft`, `validationIssue`, `responseText`, `committedAppointmentId`, `messages` (append-only, via a `concat` reducer), plus `requestId`/`graphRunId` for tracing.
- **`booklyNodes.ts`** (625 lines, the largest file here) — every node implementation: `classifyIntentNode`, `selectResourceNode`, `checkAvailabilityNode`, `buildBookingDraftNode` (this is where slot times are surfaced proactively on the *first* ask, not just after a bad guess — `formatSlotTimes`), `confirmWithCustomerNode`, `finalValidationNode`, `commitBookingNode` (calls `src/services/booklyBooking.service.ts`'s `commitBooking` — never Bookly's API directly), `appointmentStatusLookupNode`, `addNoteNode`, `cancelAppointmentNode`, `rescheduleAppointmentNode`, `pricingQuestionNode`, `offerWaitlistNode`.
- **`booklyGraph.ts`** — wires the above into a real `StateGraph`: `classify_intent` branches by intent into booking (`select_resource` → `check_availability` → either `offer_waitlist` (no slots) or `build_booking_draft`) or one of the direct-action intents (status lookup, add note, reschedule, cancel, pricing). The booking path loops `build_booking_draft` ⇄ `final_validation` until validation passes, then `commit_booking`. `getBooklyGraph()` compiles the graph once (module-level cache) with the shared checkpointer attached.
- **`booklyEntrypoint.ts`** — `tryAnswerWithBooklyGraph(chatbotId, conversationId, question, requestId)`, called from `src/services/public.service.ts`'s `answerPublicChat` before the general chat pipeline gets a turn. Gates on **both** a connected Bookly resource (`hasBooklyConnected`) **and** `entitlement.plan === "full_custom"` — Bookly is Full Custom only, not available to Crawl Plus. Also runs `checkAnsweringGate` (trial/deactivation/cost-cap) before touching the graph at all. Resumes a paused graph via `graph.getState(config)` + `Command({ resume: question })` if the thread has a pending interrupt; starts fresh otherwise. Returns `{ handled: false }` (falling through to the general chat pipeline) when the classified intent is `"other"` — this graph doesn't try to answer general questions about the business, only booking-shaped ones.

### Customer-facing commerce flow (WooCommerce)
- **`state.ts`** (`CommerceState`), **`nodes.ts`** (`classifyIntentNode`, `narrowToNamedProduct`, `productLookupNode`, `buildOrderDraftNode`, `confirmWithCustomerNode`, `finalValidationNode`, `commitOrderNode`, `orderStatusLookupNode`, `createSupportTicketNode`), **`commerceGraph.ts`**, **`commerceEntrypoint.ts`** (`tryAnswerWithCommerceGraph`) — the same propose/confirm/commit shape as Bookly, one level up in `src/services/public.service.ts`'s `answerPublicChat` (commerce is tried *before* Bookly). `commitOrderNode` calls `src/services/commerceOrder.service.ts`, never `src/lib/woocommerce/connector.ts` directly. `commerceEntrypoint.ts` also drains any queued-but-undelivered customer notifications (`commerceNotification.service.ts`) inline when the customer messages again, rather than requiring a separate delivery channel.

### Admin-chat automation (Bookly side)
- **`booklyAdminState.ts`**, **`booklyAdminNodes.ts`** (`classifyAdminIntentNode`, `buildActionDraftNode`, `confirmAdminActionNode`, `executeAdminActionNode`), **`booklyAdminGraph.ts`**, **`booklyAdminChatEntrypoint.ts`** (`answerBooklyAdminChat`) — lets a human Bookly admin manage their resource (create a resource, set availability rules/exceptions, reassign an appointment) *through chat*, using the same propose→confirm→execute shape. **This is the "authenticates differently from the customer path" piece**: `answerBooklyAdminChat` requires a real `booklyAdminToken` and calls `requireBooklyAdminSession(chatbotId, booklyAdminToken)` (`src/services/booklyAdminAuth.service.ts`, which in turn calls `src/lib/bookly/adminConnector.ts`'s `verifyAdminSession` against Bookly's own `/auth/me`) — there is no equivalent per-message auth check on the customer-facing Bookly/Commerce graphs, which instead rely on the public widget's origin check happening upstream in `public.service.ts`. `executeAdminActionNode` is the one place this graph is allowed to call `src/lib/bookly/adminConnector.ts`'s write functions.

**If you're adding a fourth graph**: follow the same file split (`xState.ts`, `xNodes.ts`, `xGraph.ts`, `xEntrypoint.ts`), reuse `checkpointer.ts`/`llm.ts` rather than standing up new singletons, and keep the actual external write inside a dedicated commit node that calls a service-layer function — never let a node call `src/lib/*`'s connector directly for anything state-changing.
