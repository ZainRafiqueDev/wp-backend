# src/lib/woocommerce

The HTTP client and deterministic business rules for the Full Custom plan's WooCommerce commerce integration (a chatbot owner connects their own WooCommerce store via `chatbot_woocommerce_credentials`: store URL + REST API consumer key/secret, encrypted at rest). Same layering as `src/lib/bookly/`: this directory is pure connector + policy, no Postgres access, no chatbot-ownership logic — that lives in `src/services/commerceOrder.service.ts`, `commerceCredentials.service.ts`, etc.

- **`types.ts`** — `WooCommerceProduct`, `WooCommerceOrder`, `CreateOrderInput` shapes.
- **`connector.ts`** — `wooFetch<T>()` backs every export (`getProduct`, `listProducts`, `checkStock`, `createOrder`, `getOrderStatus`, `buildOrderPayUrl`). Authenticates via HTTP Basic auth (base64 `consumerKey:consumerSecret`) against the store's real `/wp-json/wc/v3` REST API. Same resilience pattern as the Bookly connector: `assertSafeUrl` (`src/lib/crawler/ssrf.ts`) before every request, an 8s timeout, network/timeout failures converted to a typed `WooCommerceApiError(0, ...)` rather than a raw throw. `createOrder` always creates the order with `status: "pending"`, `set_paid: false` — ChatMate360 never marks an order paid itself, only WooCommerce's own payment gateway can (see `paymentPolicy.ts`). `buildOrderPayUrl` constructs the real WooCommerce "pay for this order" checkout link the customer is sent to — it deliberately throws (`AppError(502)`, not a silent fallback) if the store didn't return an `order_key`, since a payment URL missing its key is a broken URL, not something to paper over.
- **`paymentPolicy.ts`** — `PaymentConfirmationPolicy(order)` is the single source of truth for "is this order actually paid," and it's deliberately conservative: it trusts `order.date_paid` (WooCommerce's own gateway-set, authoritative payment-complete signal) first, then the `completed`/`processing` statuses (WooCommerce core's own documented "payment received" states) — everything else (`pending`/`on-hold`/`cancelled`/`refunded`/`failed`) is **not** treated as paid. `WooCommerceStatusMapper` turns that policy result into this codebase's own `commerce_orders.status` enum (`PAID`/`PENDING_PAYMENT`/`CANCELLED`/`REFUNDED`). This function is what a webhook handler AND the `PaymentReconciliationJob` safety-net poller both call — one policy, two callers, so a missed webhook and a reconciliation sweep can never disagree about what counts as paid.
- **`webhookSignature.ts`** — `verifyWooCommerceWebhookSignature(rawBody, signatureHeader, secret)`: HMAC-SHA256 over the *raw* (unparsed) request body, compared with `timingSafeEqual` — a webhook whose body has already been JSON-parsed can't be verified this way, so the route mounting this must use a raw-body parser ahead of JSON parsing (see `src/app.ts`'s `express.raw()` mount for `/webhooks/woocommerce/:chatbotId`, ahead of the global `express.json()`).
- **`bookingNumber.ts`** — `generateBookingNumberCandidate()`: a short, human-readable `CM-XXXXXX` code (excludes visually-ambiguous characters like `0`/`O`/`1`/`I`/`L`) generated with `crypto.randomInt` (cryptographically strong, not `Math.random`). A *candidate* — the caller is expected to retry on a real uniqueness-constraint violation rather than this module guaranteeing uniqueness itself.
