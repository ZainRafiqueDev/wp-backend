# src/lib/crawler

The website crawler that turns a customer's `websiteUrl` into `ChatbotSource[]` text content at chatbot-creation time. Runs inside the BullMQ worker process (`src/worker.ts` → `runCrawlJob` → `crawlWebsiteForChatbot`), never inside an HTTP request handler — a full crawl can take many seconds and must not block the API.

- **`crawl.ts`** — the orchestrator, `crawlWebsite(rootUrl)`. Bounded breadth-first crawl: `MAX_PAGES = 12`, `MAX_DEPTH = 3`, `CONCURRENCY = 3` concurrent workers pulling off a shared queue, same-origin links only, deduped by normalized URL (sorted query params, no trailing slash/hash). Seeds the queue from the site's real sitemap (`sitemap.ts`) in addition to just the root URL. For each page: fetches via `safeFetch`, detects an empty JS-shell (`looksLikeJsShell` — checks for a near-empty `#root`/`#app`/`#__next`-style container, a common SPA signature) and falls back to real headless-browser rendering (`renderPage.ts`) only when needed, then strips `script/style/noscript/nav/footer/svg` and extracts up to `MAX_TEXT_PER_PAGE = 6000` chars of readable text per page via `cheerio`.
- **`ssrf.ts`** — `assertSafeUrl(url)`, the shared SSRF guard reused everywhere this codebase makes an outbound request to a customer-supplied URL (Bookly connector, WooCommerce connector, the crawler itself). Rejects non-http(s) schemes, then resolves the hostname via real DNS and checks **every** returned address (not just the first) against a private/reserved IPv4/IPv6 range table — this specifically defeats DNS-rebinding attacks where a hostname resolves to a public IP at check-time but a private one at request-time, and fails closed (blocks) on any DNS resolution error or unrecognized address shape.
- **`safeFetch.ts`** — a `fetch` wrapper with `redirect: "manual"` so **every redirect hop is independently re-checked by `assertSafeUrl`** (up to `MAX_REDIRECTS = 5`) — a naive `redirect: "follow"` would let a public URL redirect straight into a private one, silently bypassing the SSRF check. Also streams the response body with a hard `maxBytes` cap, aborting mid-read rather than buffering an unbounded response.
- **`robots.ts`** — a real (if minimal) robots.txt parser (`fetchRobotsRules`, `isAllowed`), scoped to this crawler's own user-agent token `chatmate360bot`, capped at `MAX_LINES = 10000` to bound parse cost on a hostile/huge robots.txt.
- **`sitemap.ts`** — `fetchSitemapUrls(root, ...)`, best-effort `sitemap.xml` discovery to seed the crawl queue with real site URLs instead of relying purely on link-following from the homepage.
- **`renderPage.ts`** — Playwright/Chromium headless rendering, used only for pages `looksLikeJsShell` flags. Runs a **lazily-launched, process-wide singleton browser** (`getBrowser`/`closeBrowser`) — one Chromium instance is reused across every render call in the worker process, not relaunched per page. Two things worth knowing: (1) SSRF protection is enforced a *second* time here, inside the browser itself, via `context.route("**/*", ...)` — every single in-page request the rendered page makes (XHR, fetch, image, iframe — not just the top-level navigation) is checked with `assertSafeUrl` and aborted if it resolves to a private address; a page can't use client-side JS to make the browser fetch an internal address the top-level check never saw. (2) JS `dialog` events (`alert`/`confirm`/`prompt`) are auto-dismissed so a malicious or buggy page can't hang the headless browser waiting for a user who will never appear.

**Why the layered SSRF checks matter**: a customer-supplied `websiteUrl` (and, in `src/lib/bookly/` and `src/lib/woocommerce/`, a customer-supplied `base_url`) is fundamentally attacker-controlled input from the backend's point of view — it's re-validated at DNS-resolution time on every single request/redirect/in-page-fetch, not just once when the URL is first accepted, specifically because DNS answers and redirect targets can change between "looked safe" and "actually fetched."
