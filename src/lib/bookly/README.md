# src/lib/bookly

The HTTP client layer for talking to a customer's own Bookly (`helebooker`) resource — a separate, standalone booking-engine product (own repo, own database, own auth) that a chatbot owner connects to via `chatbot_bookly_credentials` (base URL + API key + resource id). Nothing in this directory owns business logic or touches Postgres directly — it's a thin, resilient fetch wrapper, one level below `src/services/booklyBooking.service.ts` and `src/services/booklyCredentials.service.ts`.

- **`types.ts`** — shared request/response shapes (`BooklyCredentials`, `BooklyAppointment`, `CreateBooklyAppointmentInput`, etc.), no logic.
- **`connector.ts`** — the **customer-facing** client, used for a chatbot's own conversational booking flow. A single private `booklyFetch<T>()` helper backs every export (`getAvailableSlots`, `createAppointment`, `getAppointment`, `cancelAppointment`, `addNote`, `rescheduleAppointment`, `getServiceInfo`, `joinWaitlist`, `getMeetingHistoryReportPdf`). Authenticates with the chatbot's own long-lived, encrypted `apiKey` (decrypted just before use by `booklyCredentials.service.ts`).
- **`adminConnector.ts`** — a **separate** client for the admin-chat automation path (`src/langgraph/booklyAdminNodes.ts` / `src/services/booklyAdmin.service.ts`). Authenticates with a real human admin/staff's own short-lived Bookly session token (`verifyAdminSession` calls Bookly's own `/auth/me` to confirm it's still valid and to read back the caller's `role`/`is_active`), not the chatbot's stored API key — an admin acting through chat can only do what their own Bookly account is actually allowed to do (`createResource`, `createAvailabilityRule`, `createException`, `reassignAppointment`, `getAppointment`). This is the "authenticates differently from the customer path" split: `connector.ts` = one long-lived per-chatbot secret, `adminConnector.ts` = one short-lived per-human session.

**Resilience, shared by both connectors' fetch helpers:**
- `assertSafeUrl(url)` (`src/lib/crawler/ssrf.ts`) runs before every single request — the customer-supplied `base_url` is treated as untrusted input and re-validated on every call, not just once at connect-time.
- 8-second timeout (`AbortSignal.timeout(REQUEST_TIMEOUT_MS)`) on every request.
- A network failure or timeout is caught and re-thrown as `BooklyApiError(0, "Could not reach the Bookly server.")` / `BooklyAdminApiError(0, ...)` — callers always get a typed error with a clear message, never a raw unhandled rejection. `isBooklyConflict(err)` lets a caller specifically detect a 409 (double-booking race) without string-matching the message.

Neither file ever reads `chatbot_bookly_credentials` or any other table directly — `creds`/`baseUrl`+`token` are always passed in by the caller, which is what keeps this layer testable and free of any cross-tenant risk of its own (the isolation guarantee lives one layer up, in the services that fetch credentials scoped to `chatbot_id`).
