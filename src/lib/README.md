# src/lib

Framework-agnostic building blocks — no Express `Request`/`Response` types appear in this directory (except where a file explicitly wraps a shared cross-cutting concern like SSRF or crypto for a controller to use). This is the layer `src/services/` is built on top of. Subdirectories `bookly/`, `crawler/`, `woocommerce/` each have their own README; this one covers the ~25 files directly in `src/lib/`.

### The chat-answering core
- **`ai.ts`** (503 lines, the largest file in the whole backend) — the multi-provider fallback chain (Claude → Gemini → OpenAI → Ollama, each skipped if unconfigured), real `tools`/function-calling for Claude and OpenAI, and `buildSystemPrompt` — the three-tier context prompt (LIVE DATA / CRAWLED PAGE CONTENT / UPLOADED DOCUMENT CONTENT) plus the `_SCOPE_GUARD`/`_GROUNDING_GUARD`/`_INJECTION_GUARD` anti-hallucination instructions.
- **`answerChatbotQuestion.ts`** (255 lines) — the real orchestrator a chat message goes through: answering-gate check → entitlement fetch (once, reused for both document-lookup gating and cost-cap reservation) → merge live-data/backend-link/crawled/document pages → cache check → relevance check → model selection → cost-cap reservation → `ai.ts` call → usage recording → post-generation grounding check (swap for fallback if it fails) → cache the result.
- **`answerFromSources.ts`** — the deterministic keyword-matching fallback used only when **no** AI provider key is configured at all (not used when a key exists but the question is off-topic — that's `relevance.ts`'s job, which produces a *different* fallback path).
- **`relevance.ts`** — `hasRelevantContent(question, pages)`: a cheap keyword-overlap pre-check (ignoring a stopword list) run *before* spending an AI call, so an obviously off-topic question gets the fallback message without ever reaching a provider. WP-2.3 hybrid retrieval is what finds SKU/id chunks; this gate only scores pages already retrieved.
- **`hybridRetrieval.ts`** — RRF fuse of lexical + vector ranked chunks (`RETRIEVAL_MODE=hybrid`, rollback `vector`). See `docs/HYBRID_RETRIEVAL.md`.
- **`embeddingPricing.ts`** — fail-closed embedding $/1M rates, token estimate, and active model/dim (`resolveEmbeddingIdentity`). Missing prices throw; a dim other than 1536 cannot be stored.
- **`embeddingBudget.ts`** — per-account daily embedding ledger (`embedding_usage_daily`) plus `embed.calls` / `embed.blocked_budget` metrics. See `docs/EMBEDDING_BUDGET.md`.
- **`ragEval.ts` / `ragEvalMetrics.ts`** — WP-2.5 labeled RAG gate (Recall@K, MRR, nDCG, grounded-answer and hallucination rates). See `docs/RAG_EVAL.md`.
- **`adminMetrics.ts`** — `admin.plan_activated` (WP-2.6) plus `adminActivatedCustomerId` used to detach admin-activated Full Custom from Stripe.
- **`groundingCheck.ts`** — `verifyGroundedClaims`, a regex-based **post-generation** check: extracts checkable-looking claims (prices, etc.) from the AI's answer and confirms they appear verbatim in the real context; a failed check swaps the answer for the fallback message rather than showing an unverified claim. Known limitation (logged in `PROJECT_STATE.md`/`RISK_LOG.md`): this can catch a hallucinated answer, it cannot catch a *poisoned context* (garbage-in-garbage-out isn't this check's job).
- **`aiPricing.ts`** — `estimateCostUsd(model, inputTokens, outputTokens)`, the $/1M-token rate table (overridable via `AI_PRICING_OVERRIDES_JSON` without a redeploy) — every usage-metering number in the system traces back to this one function.

### Document ingestion (Crawl Plus+, built alongside the daily/weekly usage work)
- **`documentParsing.ts`** — `detectDocumentType`/`extractText`: real extraction for PDF (`pdf-parse`), DOCX (`mammoth`), XLSX (`exceljs` — not `xlsx`/SheetJS, deliberately, over an unpatched CVE), TXT/MD/CSV (plain read).
- **`documentQualityCheck.ts`** — `verifyExtractedText`: a free printable-character-ratio heuristic, then (only if `OPENAI_API_KEY` is set) an OpenAI call judging whether the text reads as genuine content vs. extraction noise. Both passes fail-open on their *own* errors (OpenAI unreachable ≠ reject the document) but fail-closed on what they're actually checking (garbled text ≠ accept the document).
- **`semanticChunk.ts`** — `semanticChunk(text, options)`: WP-3.3 semantic chunking — heading/table/paragraph structure aware, tables never split mid-row, tail-overlapped, configurable target size (default 1200 chars, per-chatbot via `chatbots.chunk_target_chars`) — feeding `src/services/documentIngestion.service.ts`'s embedding step. `embeddingTextFor(chunk)` prepends heading context for the embedding call only.

### Chatbot domain types & ownership
- **`chatbot.ts`** — the `Chatbot`/`ChatbotSource`/`ChatbotTheme` types, `chatbotRowToChatbot` (DB row → domain object), `hashPageContent` (sha256, backs incremental re-crawl's change detection), `defaultFallbackMessage`. **Note**: `ChatbotSource.content` is optional and, for onboarding-time `pdf`/`word` sources, is never actually populated — see `PROJECT_STATE.md` §2's document-ingestion split.
- **`chatbotOwnership.ts`** — `requireOwnedChatbotId(userId, chatbotId)`: the one-line check nearly every service function in `src/services/` calls before doing anything with a `chatbotId` a client supplied — throws 404 if that chatbot doesn't belong to that user. This is the actual cross-tenant-isolation enforcement point referenced throughout `PROJECT_STATE.md` §4.6. WP-3.1 also writes `app.user_id` / `app.chatbot_id` here so RLS can bind after the application check succeeds.
- **`tenantContext.ts`** — request/job AsyncLocalStorage for RLS GUCs. See `docs/RLS.md`.
- **`liveData.ts`** — `LiveDataEntry` type + `liveDataRowToEntry`, backing the owner-set key/value facts (`chatbot_live_data`) merged into AI context ahead of crawled content.
- **`actions.ts`** — `ChatbotAction`/`ActionToolDef`/`ToolCallResult`/`ToolExecutor` types + `actionRowToAction`, the Custom Actions domain shapes consumed by `actionExecutor.ts` and `ai.ts`'s tool-calling.
- **`actionExecutor.ts`** — `validateActionParams` + `executeAction`: fills a Custom Action's `{{templated}}` URL/headers/body, runs `assertSafeUrl` (same SSRF guard as the crawler/Bookly/WooCommerce connectors — the fourth consumer), 4s timeout, response capped to 4000 chars, and — like the other connectors — converts any failure into a clean `{content: "...unavailable...", isError: true}` rather than throwing.
- **`backendLink.ts`** — `fetchBackendLiveContext`: the "structured pre-fetch" live-data source (distinct from Custom Actions' real tool-calling and from Bookly/WooCommerce) — hits a chatbot owner's own generic backend's `/products` and `/products/:id/availability` endpoints, capped and cached per `cacheVersion`. This is deliberately *not* the LLM deciding when to call it — it always runs, its results are just merged into context like crawled pages are.

### Plans
- **`plans.ts`** — `PLAN_DEFINITIONS` for `free`/`crawl_plus`/`full_custom`: `maxChatbots`, `allowedModels`, `perModelCapUsd`/`perModelDailyCapUsd`/`perModelWeeklyCapUsd`, `documentIngestion`. As of this pass, **all three plans allow all three model providers** (`["anthropic", "openai", "gemini"]`) — Free is differentiated by its (much tighter) cost caps, not by being restricted to one model. **Stale env var**: `FREE_PLAN_MODEL`/`env.freePlanModel` still exists in `src/env.ts`/`.env.example` but is no longer referenced anywhere in `plans.ts` or elsewhere in `src/` (confirmed by a full-repo grep) — it was the old single-model gate for Free before that changed; safe to remove, currently just dead config.

### Cross-cutting infra
- **`db.ts`** — the shared `pg` `Pool`, `null` when `DATABASE_URL` isn't set. WP-3.1 wraps `query`/`connect` with tenant GUCs (`src/lib/tenantContext.ts`): `pool.query` uses `BEGIN` + `SET LOCAL`; `pool.connect()` uses session `set_config`. Superuser connections bypass RLS and log `rls.bypass_role`.
- **`redis.ts`** — the shared `ioredis` client, `maxRetriesPerRequest: null` (lets `rate-limiter-flexible` and BullMQ manage their own retry/backoff semantics rather than ioredis silently giving up early).
- **`cache.ts`** — `getCached`/`setCached` (generic Redis JSON cache), `getChatbotCacheVersion`/`bumpChatbotCacheVersion` (the version-number pattern every per-chatbot cache key includes — bumping it is how a live-data write or re-crawl invalidates every cached answer/page/relevance-check for that chatbot in O(1), without hunting down and deleting individual keys), `normalizeQuestionKey`.
- **`crypto.ts`** — `encryptSecret`/`decryptSecret`, backing every `*_encrypted` column (`chatbot_integrations`, `chatbot_woocommerce_credentials`, `chatbot_bookly_credentials`).
- **`auth.ts`** (133 lines) — JWT signing/verification for every token type this app issues: customer access/refresh, admin access, Google OAuth CSRF `state`, and (per `CHATMATE360_SESSION_UPDATE.md`) OTP proof tokens (`signOtpProofToken`/`verifyOtpProofToken`, `typ: "otp_proof"`) — each with its own `typ` claim so one token type can never be replayed as another.
- **`errors.ts`** — `AppError(status, message)`, the one error type `src/middleware/errorHandler.ts` gives a clean, specific JSON response; anything else becomes a generic logged 500.
- **`logger.ts`** — the shared `pino` instance (`baseLogger`/`log()`), plus `chatMessageSummary`/`chatMessageDebugField`/`shortRef` helpers used to log chat content at a safe, truncated/hashed granularity by default (full content only at `debug` level) rather than logging raw customer messages at `info`.
- **`requestContext.ts`** — `runWithRequestId`/`currentRequestId`, an `AsyncLocalStorage` wrapper so `logger.ts` can tag every log line with the current request id without threading it through every function signature (see `src/middleware/README.md`'s `requestId.ts` entry).
- **`originAllowed.ts`** — `originAllowed(origin, allowedDomain)`: exact-or-subdomain hostname match, the core check behind the embed widget's per-chatbot domain authorization (`src/services/public.service.ts`).
- **`queue.ts`** / **`commerceQueue.ts`** / **`ingestQueue.ts`** — BullMQ job-enqueue helpers for the crawl queue (`enqueueCrawlJob`, `enqueueRecrawlJob`, the recrawl repeat-job scheduler), the commerce queue (webhook processing, payment-reconciliation ticks, catalog sync), and the document-ingest queue (`enqueueDocumentIngestJob`, stale-processing sweep). Three separate named queues (`CRAWL_QUEUE_NAME`/`COMMERCE_QUEUE_NAME`/`DOCUMENT_INGEST_QUEUE_NAME`) since crawl, commerce/payment, and document embed jobs are operationally distinct workloads. All are enqueue-only here; the actual job processors live in `src/worker.ts`.
- **`objectStorage.ts`** — put/get/delete for uploaded document bytes (`fs` or `s3`). Keys are `tenant/{chatbotId}/documents/{documentId}/...`.
- **`ingestMetrics.ts`** — `ingest.queue_depth` / `ingest.processing_age` / `ingest.failed`. Redis failures never take ingest down.
- **`email.ts`** — `sendEmail`, real transactional email via Resend's HTTP API when `RESEND_API_KEY` is set; when it isn't, logs the would-be email (via both `pino` and a plain `console.log`) and returns `{delivered: false}` instead of failing — safe default for local dev, never silently pretends to have sent something in production.
- **`stripe.ts`** — `stripeClient()` (lazy singleton), the plan-code ↔ Stripe Price ID mapping (`priceIdForPlan`/`planForPriceId`/`priceIdForTopupModel`) — this is what keeps a real Price ID out of the browser (see `src/validators/README.md`'s billing note): the client sends `plan: "crawl_plus"`, the server looks up the real `price_...` id from here.
