# src/services

The business-logic layer — 41 files, ~6,100 lines, the bulk of this backend. Every function here that touches a user-supplied `chatbotId` starts by resolving ownership via `src/lib/chatbotOwnership.ts`'s `requireOwnedChatbotId(userId, chatbotId)` (or, for the public/tool-calling paths, `src/services/toolAuthorization.service.ts`'s `authorizeToolCall`) — that's the actual cross-tenant-isolation enforcement point, not something routes or controllers do. Grouped below by domain rather than alphabetically, since the flat file list doesn't communicate how these actually relate.

### Auth & account
- **`auth.service.ts`** (440 lines, one of the two largest files here) — `signup`/`login`/`getMe`/`refreshSession`/`logout`, full Google OAuth (`startGoogleOAuth`/`completeGoogleOAuthCallback`), legacy link-based `verifyEmail`/`resendVerification`, `requestPasswordReset`/`resetPassword`, `setAutoPurchase`. **Password signups start `email_verified = false`**; Google signups are auto-verified (Google already verified the address). `src/services/chatbot.service.ts`'s `createChatbot` checks `email_verified` and blocks chatbot creation until it's true — a real, active gate, not cosmetic.
- **`otp.service.ts`** (261 lines, new) — `sendOtp`/`verifyOtp`, purpose-scoped (`EMAIL_VERIFY`/`ORDER_ACCESS`/`SENSITIVE_ACTION` — deliberately **not** `PASSWORD_RESET`, which stays on the separate reset-token flow in `auth.service.ts`). Real security properties, all verified by reading the file: `generateOtpCode` uses `crypto.randomInt` (not `Math.random`); codes are SHA-256 hashed at rest (`auth_otps.otp_hash`, via the same `hashToken` `notification.service.ts` exports); `sendOtp`'s public response text is identical whether or not the email/account actually exists (enumeration-safe); the resend cooldown is enforced from the database, not Redis, so it still works if Redis is down; `verifyOtp` enforces expiry, a `max_attempts` ceiling, and single-use (`verified_at`). A successful verify returns a short-lived `typ: "otp_proof"` JWT (`signOtpProofToken`, `src/lib/auth.ts`) rather than silently mutating server state itself — callers decide what a valid proof token is allowed to do.
- **`notification.service.ts`** — does two distinct jobs in one file: (1) the dashboard's in-app notification inbox (`createNotification`, `listNotificationsForUser`, `markNotificationRead`/`markAllNotificationsRead`); (2) shared token utilities (`hashToken`, `generateOpaqueToken`) plus `issueEmailVerification` (generates an opaque token, emails a real verification link via `src/lib/email.ts`, **and** creates an in-app notification about it) — `otp.service.ts` imports `hashToken` from here rather than duplicating it.
- **`customerIdentity.service.ts`** — a **separate** identity system from `users`, for a chatbot's own end-*customers* (not the chatbot owner): `resolveCustomerIdentity` (find-or-create by email/phone, scoped to one `chatbotId`), `VerificationLevel` (`UNVERIFIED → EMAIL_VERIFIED → ORDER_VERIFIED → ACCOUNT_VERIFIED`, `VERIFICATION_LEVEL_RANK` for comparisons), `customerBelongsToChatbot` (the actual per-customer cross-tenant check used by `toolAuthorization.service.ts`).
- **`autoPurchase.service.ts`** — `tryAutoPurchaseTopup`: if a user has opted in (`auto_purchase_enabled`/`auto_purchase_model` on `users`, set via `setAutoPurchase`), automatically buys a top-up credit (`topup.service.ts`) when a model's quota is exhausted mid-conversation, instead of just falling back to the "can't answer" message.

### Plans, billing, usage
- **`billing.service.ts`** (398 lines) — Stripe checkout/portal sessions, `processStripeWebhookEvent` (the real webhook handler for `checkout.session.completed`/`customer.subscription.updated`/`.deleted`/`invoice.payment_failed`), and — the most-imported thing in this whole directory — `getEntitlementForChatbot`/`getEntitlementForUser`, which resolve the real `subscriptions` table into an `Entitlement` (`src/lib/plans.ts`'s `PlanDefinition` + `active`). `clearTrialDeactivationIfEntitled` (called from the webhook sync path) clears `users.trial_deactivated` only on a genuinely entitled status — see `accessGate.service.ts` below for who sets that flag.
- **`usage.service.ts`** (405 lines, the other largest file) — token/cost metering, tracked at **day, week, and month granularity simultaneously** (`currentDayPeriod`/`currentWeekPeriod`/`currentBillingPeriod`, all written into the same `chatbot_usage` table via one `recordUsage` call — a day/week/month string all fit the same `billing_period` text column, no schema split). `isModelQuotaAvailable` checks all three windows independently (blocks if *any* is at or over cap); `reserveModelCostSlot` does the same atomically against three Redis keys, rolling back all three if any is exceeded — this is what actually prevents a burst of concurrent requests from blowing through a cap that a plain read-then-write check would miss. `getUsageSummaryForOwner` (back-compat, month-only) and `getUsageWindowSummariesForOwner` (day+week+month together, each model row carrying its own cap) both back the dashboard's usage panel.
- **`topup.service.ts`** — one-time pay-as-you-go credits (`createTopupCheckoutSession`, `creditTopup`) that offset the **monthly** cap only, deliberately never the daily/weekly ones (see the comment on `usage.service.ts`'s `getEffectiveModelCapUsd`) — a top-up is meant to extend the month's budget, not let a single day blow past its own smoothing cap. `creditTopup` requires the Stripe cash amount and fails closed unless granted AI dollars are strictly less than cash collected.
- **`accessGate.service.ts`** — `checkAnsweringGate`, the single function every answering path (`answerChatbotQuestion.ts`, the Bookly graph, the Commerce graph) calls before doing anything else. Checks, in order: `chatbots.is_active` (abuse-flagged), `users.is_active` (admin-deactivated), `users.trial_deactivated` (a **fast-path read** of a persisted flag — see next sentence), then (only if that flag isn't already set) computes live trial-expiry from `trial_started_at` and, the first time it finds an expired unpaid trial, persists it (`trial_deactivated = true`) so every subsequent check is the cheap flag read instead of re-doing the date math and an entitlement lookup every single request. Finally checks `usage.service.ts`'s `isOverCostCap`. Also exports `getAccountStatus` for the dashboard's status badge.
- **`abuseDetection.service.ts`** — `recordCacheMissAndCheckAbuse`: flags (and optionally, if `ABUSE_AUTO_DEACTIVATE=true`, deactivates) a chatbot hit with an unusually high rate of answer-cache-*misses* in a short window — a proxy for "someone is hammering this chatbot with never-before-seen questions," which is both a cost risk and a possible scraping/abuse pattern.
- **`admin.service.ts`** (256 lines) — the admin dashboard's own backing service: `adminLogin`, `listUsers`/`setUserActive`/`deleteUser` (delete requires the caller to have already passed `confirm: true` through the validator), `getUserUsageBreakdown`, `listAbuseFlags`/`markAbuseFlagReviewed`. Every mutating action here writes to `admin_audit_log` (not shown in the export list above, but every admin.service.ts write path is unconditionally paired with an audit-log insert per the file's own body).

### Chatbot lifecycle
- **`chatbot.service.ts`** (348 lines) — `createChatbot` (the email-verification + plan `maxChatbots` gate, then either an immediate crawl or a pure-`sources` chatbot with no URL), `runCrawlJob`/`crawlWebsiteForChatbot` (the actual worker-process entry points into `src/lib/crawler/`), `retryChatbotCrawl`, `listChatbots`/`getChatbotById`, the theme/domain/fallback-message/preferred-model setters, `chatWithOwnChatbot` (the authenticated dashboard preview chat, calling into `src/lib/answerChatbotQuestion.ts`).
- **`recrawl.service.ts`** — `runIncrementalRecrawl`: re-crawls a chatbot's site and replaces only the pages whose `hashPageContent` (`src/lib/chatbot.ts`) actually changed, not the whole source list — the incremental part of "incremental re-crawl." `listRecrawlCandidateChatbotIds` is what the worker's scheduled tick queries to know which chatbots are due.
- **`conversation.service.ts`** — `loadConversationContext`/`recordTurn`/`pinModelIfUnset`: session-scoped conversation memory (recent turns sent verbatim, older ones folded into a running summary once a turn-count threshold is crossed — see `CONVERSATION_CONTEXT_TURNS`/`CONVERSATION_SUMMARY_THRESHOLD_TURNS`), and "pin" the model a conversation started with so a mid-conversation model-selection change doesn't switch providers under a customer.
- **`liveData.service.ts`** — CRUD for `chatbot_live_data` (`listLiveData`/`createLiveData`/`updateLiveData`/`deleteLiveData`) plus `getLiveDataForAnswering`, the read path `answerChatbotQuestion.ts` actually calls.
- **`integration.service.ts`** — a chatbot's own backend-link config (API key + base URL) for two different consumers: Custom Actions' `executeAction` (`getDecryptedApiKeyForChatbot`) and the "structured pre-fetch" live-data source (`getBackendLinkForChatbot`, consumed by `src/lib/backendLink.ts`).
- **`customActionsAccess.service.ts`** — the shared Custom Actions entitlement rule: active Crawl Plus plus a current-month Claude or OpenAI top-up.
- **`actions.service.ts`** — Custom Actions CRUD and runtime loading. The write path enforces the shared entitlement rule; the answering path additionally requires this chatbot's encrypted backend connection and returns only topped-up, tool-capable models.
- **`documentIngestion.service.ts`** — `uploadDocument` persists bytes (`storage_key`) then returns `accepted` so the HTTP handler can 202; `processPersistedDocument` scans (WP-2.2) then embeds and writes `content_tsv`; `lookupRelevantDocumentChunks` fuses lexical + vector (WP-2.3). See `docs/ASYNC_DOCUMENT_INGEST.md` and `docs/HYBRID_RETRIEVAL.md`.
- **`malwareScan.service.ts`** — scan-before-parse for WP-2.2 (`mock` EICAR or ClamAV INSTREAM). Unclean files never chunk/embed. See `docs/MALWARE_SCAN.md`.
- **`embeddings.service.ts`** — `embedText`/`embedTexts`/`toPgVectorLiteral`: the one place `OpenAIEmbeddings` gets instantiated. Every call requires a chatbot tenant, prices the model (fail closed), reserves daily USD, and records `embedding_model`/`embedding_dim` on write. See `docs/EMBEDDING_BUDGET.md`.
- **`modelSelection.service.ts`** — `selectModelForNewConversation` walks `env.modelPriorityOrder` (default `openai,anthropic,gemini` — see `src/lib/README.md`'s note that Free is no longer restricted to one model) and picks the first provider both allowed by the plan and under quota; `selectModelForConversation` layers a manual `preferredModel` override on top, falling back to auto-selection if the preference isn't plan-allowed or is out of quota.
- **`analytics.service.ts`** — `getAnalyticsForChatbot`, backing the dashboard's `/chatbots/:id/analytics` panel (new alongside the OTP/billing work — not covered in earlier status docs).

### Bookly integration
- **`booklyCredentials.service.ts`** (256 lines) — connect/disconnect/status for a chatbot's own Bookly resource, `getDecryptedBooklyCredentials` (the only place the encrypted API key is decrypted for the customer-facing path), `listBooklyResourceOptions`/`addBooklyResource` (multi-resource support), `downloadBooklyMeetingHistoryReport`.
- **`booklyBooking.service.ts`** (281 lines) — **the commit boundary**. `commitBooking` (line 90) is the only function in the entire codebase allowed to call `src/lib/bookly/connector.ts`'s `createAppointment` — confirmed by grep, not assumed. It claims an idempotency key atomically (`insert ... on conflict (chatbot_id, idempotency_key) do nothing returning *`) before ever calling Bookly; losing the claim means either replaying an already-`CONFIRMED` result or a clean 409 if another attempt is still in flight. Also owns `checkAvailabilityForChatbot`, `cancelBookingForCustomer`, `rescheduleBookingForCustomer`, `addNoteToBooking`, `joinWaitlistForChatbot`, `getServiceInfoForChatbot`.
- **`booklyAdmin.service.ts`**, **`booklyAdminAuth.service.ts`**, **`booklyAdminAudit.service.ts`** — the separate admin-chat-automation path: `requireBooklyAdminSession` (verifies the human admin's own Bookly session token, not the chatbot's stored API key — see `src/langgraph/README.md`), `createResourceAsAdmin`/`setAvailabilityRuleAsAdmin`/`reassignAppointmentAsAdmin`/`addExceptionAsAdmin` (calling `src/lib/bookly/adminConnector.ts`), and `recordAdminAction`/`listAdminAuditLogForChatbot` (the audit trail every admin action writes to, unconditionally).

### WooCommerce / commerce
- **`commerceCredentials.service.ts`** — connect/disconnect/status for a chatbot's WooCommerce store, `requireFullCustomPlan` (defined here, imported by `actions.service.ts` too), `getDecryptedWooCommerceCredentials`/`getDecryptedWebhookSecret`.
- **`productCatalog.service.ts`** — `syncProductCatalog`/`resyncSingleProduct` (pulls the real WooCommerce catalog into `product_catalog_cache` with embeddings), `lookupProducts` (pgvector similarity search), `getLiveProductSnapshot` (a live stock/price check bypassing the cache for a specific product).
- **`orderState.service.ts`** — the **order state machine**: `VALID_TRANSITIONS` is an explicit table (`DRAFT → PENDING_PAYMENT → PAID → PROCESSING → SHIPPED → DELIVERED`, plus `CANCELLED`/`REFUNDED` branches) — `transitionOrderState` rejects an invalid jump rather than silently allowing it. This is the layer both a webhook and the reconciliation job call into, so they can never disagree about what state an order is allowed to move to next.
- **`commerceOrder.service.ts`** — `commitOrder` (creates the real WooCommerce order via `src/lib/woocommerce/connector.ts`, generates a `bookingNumber` — retrying on collision — and writes the initial `commerce_orders` row through `orderState.service.ts`), `getOrderForCustomer`.
- **`commerceWebhookReceive.service.ts`** / **`commerceWebhookProcessing.service.ts`** — split receive-vs-process: the receive side verifies the signature (`verifyWooCommerceWebhookSignature`) and records the raw event (`commerce_webhook_events`) fast so WooCommerce gets a quick 200; the processing side (run from the BullMQ commerce queue, `src/lib/commerceQueue.ts`) is what actually calls `orderState.service.ts` based on the event.
- **`paymentReconciliation.service.ts`** — `runPaymentReconciliation`, the scheduled safety net for a webhook that never arrived: re-checks any order stuck in `PENDING_PAYMENT` past a threshold directly against WooCommerce's own order-status API and calls the same `orderState.service.ts` transition path a webhook would have.
- **`commerceNotification.service.ts`** — `createPaymentConfirmedNotification`/`drainUndeliveredNotifications`: queues a "your payment was confirmed" message for a customer and delivers it the next time they message the chatbot (there's no push channel to a chat widget, so delivery is "next time they're back").
- **`commerceTicket.service.ts`** — `createTicket`/`getTicketForCustomer`, the support-ticket escalation path the Commerce graph's `createSupportTicketNode` calls.

### Cross-cutting authorization
- **`toolAuthorization.service.ts`** (204 lines) — the single authorization matrix for **every** tool-calling operation across Bookly, Commerce, and Bookly-admin (`ToolOperation` — 18 variants, from `lookup_product` to `admin_reassign_appointment`). `REQUIRED_VERIFICATION` maps each operation to the minimum `VerificationLevel` a customer identity needs (many are `null` — no verification required — but e.g. `get_order_status`/`get_ticket_status` require `ORDER_VERIFIED`). `authorizeToolCall` is the one function that actually enforces this, called from `productCatalog.service.ts`'s `lookupProducts` and presumably the equivalent Bookly/Commerce tool entry points. If you add an 19th tool operation anywhere in the system, it needs an entry in this file's map or it silently defaults to whatever `REQUIRED_VERIFICATION`'s fallback behavior is — check the file directly before assuming.

### Public/marketing (no auth, no chatbot ownership)
- **`public.service.ts`** — `authorizePublicRequest`/`getPublicChatbot`/`answerPublicChat`, the embed widget's own backend — see `PROJECT_STATE.md` §4 and `src/routes/README.md`'s `/public` entry.
- **`demo.service.ts`** — `replyToDemoMessage`, the sandboxed marketing-site demo chat backed by `src/data/demo-replies.json`.
- **`contact.service.ts`**, **`trial.service.ts`**, **`waitlist.service.ts`** — one-function files for the matching marketing-site forms (`contact_submissions`, `trial_signups`, `waitlist`).

**If you're adding a new service file**: put the ownership/authorization check at the very top of every exported function that takes a `chatbotId` or `userId` from a caller — don't assume the controller already checked it, since a controller here never does.
