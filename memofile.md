## 2026-09-29 update: production-hardening audit + 5 Critical fixes

A full audit was run against this repo (published as a Claude Docs artifact — ask the user for the link if needed) using a "Principal Staff Engineer" review prompt covering architecture, memory, DB, Redis, AI/RAG, security, observability, testing, and AWS. Headline: **this is not a from-scratch rewrite candidate** — RLS is real and enforced, connection pooling is correct, a regression-gated RAG eval harness already exists, CI runs against real Postgres/Redis. The findings are specific, identifiable gaps.

Of the 6 Critical findings, **5 are now fixed and fully tested** (121/121 test files, 650/650 tests passing):

1. **Env validation at boot** (`src/env.ts`) — added a scoped zod schema (`bootEnvSchema`/`validateBootEnv`) that format-checks only the handful of connection/secret vars whose malformed-but-present value causes silent failure (`databaseUrl`, `redisUrl`, `frontendUrl`, `jwtSecret`, `integrationEncryptionKey`, `stripeSecretKey`, `stripeWebhookSecret`, `sentryDsn`) — deliberately NOT a full 183-var rewrite, since most vars are tuning knobs with safe fallbacks already. **Important nuance**: today's actual two incidents (dead Redis port, wrong CORS origin) were both *syntactically valid URLs pointing at the wrong place* — a format check alone would NOT have caught either. The real fix for that class of bug is `src/index.ts`'s new boot-time Redis reachability ping (`Promise.race` against a 3s timeout, since `redis.ping()` itself would hang forever given `maxRetriesPerRequest: null`) — logs a loud `baseLogger.error` instead of silently hanging. Verified live both ways: happy path logs "redis reachable at boot"; a deliberately-reintroduced dead port (`REDIS_URL=redis://127.0.0.1:6380`) produces a loud error within 3s instead of a silent multi-hour hang.
2. **Customer login rate limit** — `/auth/login` had none (unlike `/admin/login`). 3. **PgBouncer image tag** — the broken tag flagged earlier this session (`v1.22.1-p1`, a 404) was temporarily patched to `:latest`; now pinned properly to `edoburu/pgbouncer:v1.25.2-p0` (found via the real Docker Hub tags API — note the real tags use a `v` prefix and `-pN` suffix). Verified live twice: once via a manual container-to-container `SET LOCAL` test, and again after repinning to the exact version tag.
4. **Admin user list pagination** — was hard-capped at 200 rows with no way to see further accounts. `listUsers()` in `src/services/admin.service.ts` now takes `limit`/`offset` (default 50, max 100, clamped server-side — never trusts the client value directly), returns `{ users, totalCount }` via a new `AdminUserListPage` type, runs a matching `COUNT(*)` query. Frontend (`Chatmate360-main/components/admin/pages/users-page.tsx`) has real Prev/Next page controls now. 4 new backend tests in `tests/integration/adminUserPagination.integration.test.ts`. **Not independently browser-verified** — hit an environment issue (the actual Chrome window was minimized/0-width, `Cannot take screenshot with 0 width`) that I couldn't resolve from the tool side. Typecheck/lint clean, reuses already-proven `SmallButton`/`SectionCard`/`adminApi` components. If you're picking this up, do a quick visual pass on `/admin/users` with >50 accounts in the DB before considering it fully done.
5. **Sentry error tracking** — `src/lib/sentry.ts` (new). `initSentry()` called at the top of `src/app.ts` (before route registration); warns loudly at boot if `SENTRY_DSN` is unset but never crashes. `installSentryErrorHandler(app)` wired in after the 404 handler and before this app's own `errorHandler`, so Sentry sees every error but the JSON response shape is unchanged. ## What was just completed: WP-3.2 (Full Hybrid Retrieval with Reranking)

The lexical+vector hybrid retrieval fusion (RRF) already existed (`src/lib/hybridRetrieval.ts`, `WP-2.3` in this repo's own docs) — it was documented as explicitly deferring rerank ("Rerank is Phase 4"). This session added the missing rerank stage on top of it.

### Design decision
No cross-encoder model or reranking API (Cohere, etc.) is configured anywhere in this stack, and adding one would mean a new paid dependency/API key not yet approved. Instead, reused the exact pattern WP-3.1's query rewriting already established: an **LLM listwise rerank** via `completeCheaply()` (the same Gemini→OpenAI cheap-completion fallback chain in `src/lib/ai.ts`, already used for query rewriting) — the fused RRF candidates are numbered and shown to the LLM, which returns a comma-separated most-to-least-relevant ordering. This needed no new provider/API key, matches the existing fail-open philosophy (any failure falls back to the plain RRF order, never breaks retrieval), and reuses the existing per-tenant usage/cost-tracking (`recordUsage`) so rerank cost is charged like any other AI call.

### New/changed files
- **`src/lib/rerank.ts`** (NEW) — `rerankChunks(chatbotId, question, candidates: FusedChunk[], topN)`. Builds a numbered-candidate prompt, calls `completeCheaply`, parses the response for an ordered list of candidate numbers (`parseRankedOrder` — robust to extra text, out-of-range numbers, duplicates; any candidate number the model's response omits is appended at the end in original order, so a parse hiccup never drops a chunk), returns the reordered+truncated list. Returns the original order unchanged (no LLM call at all) when there are ≤1 candidates or `RETRIEVAL_RERANK_ENABLED=false`. Never throws — logs a warning and falls back to the original fused order on any error (no provider configured, timeout, empty response).
- **`src/env.ts`** — added `retrievalRerankEnabled` (`RETRIEVAL_RERANK_ENABLED`, default `true`) and `retrievalRerankCandidatePool` (`RETRIEVAL_RERANK_CANDIDATE_POOL`, default `15`).
- **`.env.example`** — documented both new vars.
- **`src/services/documentIngestion.service.ts`** — `lookupRelevantDocumentChunks` now keeps a wider RRF-fused candidate pool alive (`max(limit, retrievalRerankCandidatePool)` instead of truncating straight to `limit`), passes that pool through `rerankChunks(...)`, then truncates to the real `limit`. In vector-only mode (`RETRIEVAL_MODE=vector`), `RankedChunk[]` is now mapped into the same `FusedChunk` shape so both modes flow through one rerank call site.
- **`docs/HYBRID_RETRIEVAL.md`** — rewritten to document the rerank stage, its config, its fallback/rollback behavior, and its log lines.
- **`tests/unit/rerank.test.ts`** (NEW) — 9 tests, all passing: skips LLM on 0/1 candidates, correct reordering, truncation after reorder, missing-number fallback-append, out-of-range/duplicate number handling, null-response fallback, thrown-error fallback, `RETRIEVAL_RERANK_ENABLED=false` bypass, usage/cost recording.

### Real bug caught and fixed while verifying no regressions (important — read this if you see test timeouts)
Adding a real LLM call inside `lookupRelevantDocumentChunks` broke 4 **pre-existing** tests that call that function directly (or seed document chunks and hit it) without mocking `src/lib/ai.js` — because this environment's `.env` has **real** `GEMINI_API_KEY`/`OPENAI_API_KEY` configured, so those tests started making real network calls and hit Gemini free-tier rate limits (429s), timing out at 30s. ## 2026-09-29 update: OKF crawler-triggered suggestions (relevance filter + recrawl dedup + volume cap)

Wired the website crawler into `suggestOKFConcepts` so canonical-knowledge suggestions get created from crawled pages, not just uploaded documents — guarded by three things the user explicitly required seeing designed before implementation:

1. **Relevance filter** (`src/lib/okfPageRelevance.ts`, new) — deterministic (non-LLM, avoids an AI-cost-deciding-AI-cost loop), `scoreOkfRelevance(url, text)`/`isLikelyOkfRelevantPage`. A deny list (blog/news/press/careers/about/team) short-circuits to 0 regardless of content; an allow list of ~18 URL-path patterns (pricing, refunds, terms, faq, shipping, sla, etc.) and content-signal patterns (currency, day/hour counts, named policy phrases, checked only in the first 5000 chars) each add score. 10 unit tests in `tests/unit/okfPageRelevance.test.ts`.
2. **Recrawl dedup** — before suggesting, checks `select id from okf_concepts where chatbot_id=$1 and resource_url=$2 and is_active=true limit 1`; skips if found. Verified via a specific back-and-forth with the user about what `is_active` means in this schema (it tracks dismissed-vs-not, independent of `approved_at`, which tracks pending-vs-live) — the dedup correctly catches both a still-pending AND an approved concept for the same URL, but lets a *dismissed* (`is_active=false`) one be re-suggested. That last case had no test until this session's follow-up audit — now covered.
3. **Volume cap** — `env.okfCrawlSuggestMaxPagesPerRun` (default 5), candidates sorted by relevance score descending before slicing, so the highest-signal pages win when a crawl turns up more relevant pages than the cap.

Both `recrawl.service.ts` (incremental recrawl, gated on content-hash change so unchanged pages are never reconsidered) and `chatbot.service.ts`'s `runCrawlJob` (first-time crawl, no hash gate needed since everything is new) call the shared `suggestOKFConceptsFromCrawledPages(chatbotId, pages)` entry point in `okfSuggestion.service.ts`, awaited (not fire-and-forget) since both run inside worker jobs. 17 integration tests in `tests/integration/okfCrawlSuggestion.integration.test.ts` (boilerplate skip, relevant-page suggestion, dedup, cap ordering, disabled-via-env, tenant isolation, dismiss-then-resuggest).
